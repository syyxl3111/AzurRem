所以修复方针是：**让 App 走 PC 页面同源的函数/同源的规则**，而不是在客户端"把数字调对"。

## 1. 暂停状态下「队列中」与 PC 不同步

### 现象
实例处于「已停止」时，App 的「队列中」与 PC 概览页的「队列中」内容/条数不一致。
App 里还出现过明显陈旧的时间，如「智能调度Plus · 09-09 00:00」（当天是 09-11）。

### PC 端的真实逻辑
`module/webui/app_dashboard.py:35-58`（`alas_update_overview_task`，概览页每次刷新的入口）：

```python
self.alas_config.load()
self.alas_config.get_next_task()          # ★ 重新计算 pending_task / waiting_task

if len(self.alas_config.pending_task) >= 1:
    if self.alas.alive:                   # ★ 运行时
        running = self.alas_config.pending_task[:1]   # 第一个 = 正在跑
        pending = self.alas_config.pending_task[1:]   # 其余 = 队列中
    else:                                 # ★ 停止时
        running = []                      # 运行中直接置空
        pending = self.alas_config.pending_task[:]    # 全部进队列中，一个不减
else:
    running = []
    pending = []
waiting = self.alas_config.waiting_task
```

页面上是三段：**运行中 / 队列中 / 等待中**（`module/webui/app_overview.py:64-87`）。

`get_next_task()` 在 `module/config/config.py:312-342`，规则是：

```python
now = current_time()                       # 可用 is_hoarding_task / hoarding 偏移
for func in self.data.values():
    if not func.enable: continue
    if not isinstance(func.next_run, datetime): error.append(func)   # ★ 解析失败也算"该跑"
    elif func.next_run < now:                   pending.append(func)
    else:                                       waiting.append(func)
pending = Filter(regex=r"(.*)", attr=["command"]).load(SCHEDULER_PRIORITY).apply(pending)  # ★ 优先级排序
waiting = sorted(waiting, key=attrgetter("next_run"))
if error: pending = error + pending        # ★ 解析失败的任务排在最前面
```

### ⚠️ 一个重要的纠正
一开始我判断这是"App 走了旁路接口"，**不对**。

`module/webui/app.py:395` 是 `application.mount("/mcp", mcp_app)` ——
MCP 和 WebUI **同一个进程、同一个 CWD、同一份 `config/alas.json`**。
实测两边（项目自带 venv 直接跑）**19 个启用任务集合逐字相同**。

所以**数据源没问题，差别全在"拿到数据之后怎么算"**：分桶 / 排序 / 命名。
而且 `mcp_server_sse.py:367` 那 6 个跳过名单是**空操作**
（Alas/Dashboard 没有 Scheduler 组，其余 4 个在 args.json 里根本不存在），
过滤条件与 WebUI 等价。

### App 端错在哪（实测数据）
`mcp_server_sse.py:362-374` 返回扁平数组，App 用 `Models.kt:190 splitQueue`
按 `epoch <= now` 自己切两半。实测（2026-09-11 10:19，实例 alas）：

```
WebUI 队列中(停止) : [OpsiAshBeacon 09-11 09:57:48, OpsiScheduling 09-09 00:00:00]
App   队列中(<=now): [OpsiScheduling 09-09 00:00:00, OpsiAshBeacon 09-11 09:57:48]  ← 顺序相反
alive=True         : WebUI 运行中=[OpsiAshBeacon]，队列中=[OpsiScheduling]
                     App 队列中=2 项                                              ← 多一项
等待中             : 两边顺序一致 ✅
```

对应到代码：

1. **【高】少一个桶**：WebUI 是三桶 + `alive` 判定，App 只有两桶。
   停止时集合恰好相同（所以你没立刻发现），但实例**活着但暂停**（state=1/3）时，
   App 会把 WebUI 放在「运行中」的那一个也算进「队列中」。
2. **【高】「队列中」的排序键错了**：WebUI 排的是 **`SCHEDULER_PRIORITY` 优先级序**，
   App 排的是时间序 ⇒ **App「队列中」第一条不是下一个真要跑的任务**。
   本机自定义优先级在 `General.YukikazeTaskManager.TaskPriorityAdjustment`（实测 `OpsiAshBeacon` 排在 `OpsiScheduling` 前）。
3. **【中】没翻译**：MCP 返回的是顶层 group key 英文名，
   WebUI 用 `t(f"Task.{cmd}.name")`。
4. **【中】没算 `hoarding` 偏移和严格 `<`**：WebUI 是 `next_run < now - hoarding`，
   App 是 `<= now`。当前 hoarding = 0，属潜在坑。
5. **【中】时间解析**：必须按 `yyyy-MM-dd HH:mm:ss` 在 **Asia/Shanghai** 解析
   （NTP 校时，`time_source.py:148-155`），不能字符串比较、也不能当 UTC。

### 为什么 `09-09 00:00` 这种陈旧值会出现（不是 bug）
`OpsiScheduling` 的 `ServerUpdate: "00:00"` —— 每次跑完 `task_delay(server_update=True)`
都会把 NextRun 算到**下一个零点**（`utils.py:450-473`），所以它的 NextRun **永远是整点**。
上次 09-08 跑完被排到 09-09 00:00:00，之后实例一直停着、**没人再推进 NextRun**，就冻结在那儿了。
`NextRun` 的语义是"最早可再次运行的时刻"，**过去时间 = 逾期积压，不是故障**。

> ⚠️ 顺带发现：`mcp_server_sse.py:392-396 clear_scheduler_queue`
> **只关 `Enable`、不清 `NextRun`**，所以"清空队列"之后配置里仍留着陈旧值。

### 修复方案
桥新增只读接口 `/api/overview_tasks`，**复刻 `app_dashboard.py:35-58` 的逻辑**：

```json
{"alive": true, "running": [...], "pending": [...], "waiting": [...], "waitingAll": [...]}
```

顺序**照搬** `pending_task` / `waiting_task`，任务名附 i18n 中文 `name`。

### ⚠️ 关键：扩展点必须是**未跟踪的桥**，不能是 MCP server
调研建议"新增/扩展 MCP 工具"，但 **`mcp_server_sse.py` 是被 git 跟踪的文件**
—— 往里面加工具，下次 `git reset --hard` 100% 被 revert。
所以这个接口只能加进**未跟踪的 sidecar**（`mobile_bridge.py` 模式）。

### 工作量与风险
`SCHEDULER_PRIORITY` 不是配置里的静态字段，而是运行时算出来的
（`module/config/config_manual.py:107-136`）：

```
merge_task_priority(
    用户在 alas.json 的 YukikazeTaskManager.TaskPriorityAdjustment,
    args.json 里的默认值（config_manual.py:53-80 的 _DEFAULT_SCHEDULER_PRIORITY）,
    get_scheduler_tasks(args),          # module/config/task_priority.py:47
)                                       # module/config/task_priority.py:91
```

桥要复刻的话得连 `task_priority.py` 的两个函数一起移植，**中等工作量**。
`alive` 可以从 MCP `get_status`（返回 `running` / `state`）拿，不用桥管。

**建议分两步**：

| 步骤 | 内容 | 效果 |
|---|---|---|
| 第一步 | 补「运行中」分组 + `alive` 分支 + 中文名 | 立刻可见，解决你反馈的现象 |
| 第二步 | 移植 `task_priority.py`，让「队列中」按优先级排序 | 顺序与 PC 完全一致 |

第一步做完就能对数；第二步单独验收。

### 另需确认
- `hoarding`（囤积模式时间偏移，`config.py:318-319`）—— 调研说是
  `Alas.Optimization.TaskHoardingDuration`，**若确实在 `alas.json` 里，桥就能直接读**，
  需实测确认；`is_hoarding_task` 本身是运行时类标志，但 `get_next_task()` 里它只在
  「上一次没有待处理任务」时为 True，停止状态下通常为 False。
- 也可以让桥 `import` 项目自己的 `AzurLaneConfig` 直接调 `get_next_task()`（保真度最高），
  但构造 `AzurLaneConfig` 有副作用（设备 ID 初始化、可能的自动迁移），
  **与"不改动"约束冲突，暂不采用**。

### 验收
停止 / 运行两种状态下，App「任务」Tab 的三段与 PC 概览页逐条对齐（**数量 + 顺序 + 时间**）。
用上面那组实测数据当基准：
- 停止时「队列中」应是 `[OpsiAshBeacon, OpsiScheduling]`（**优先级序，不是时间序**）
- 运行时应是「运行中 `[OpsiAshBeacon]` + 队列中 `[OpsiScheduling]`」

## 2. 侵蚀1「出击消耗」「净赚体力」与 PC 不一致

### 现象（PC 截图 vs App 截图，同一月份 2026-09）

| 列 | PC WebUI | App 显示 | `/api/cl1_stats` 原始返回 |
|---|---|---|---|
| 战斗场次 | 10120 | 9,525（当时） | battle_count |
| 战斗轮次 | 5060 | 4,762（当时） | battle_rounds |
| **出击消耗** | **25300** | **571,440** | sortie_cost |
| 遇见明石次数 | 248 | 227（当时） | akashi_encounters |
| 吊机次数 | 243 | 230（当时） | siren_research_devices |
| 平均体力 | 115 | 115.2 | average_stamina |
| **净赚体力** | **3240** | **26150** | net_stamina_gain |

### 根因（已用硬盘数据验证）
**PC 页面和 REST API 对同名列用了两套完全不同的公式。**

PC 页面 `module/webui/app_stat_opsi.py:159-307`（`_build_cl1_summary`）：
```python
tb = int(summary.get("total_battles"))     # 战斗场次
rounds = (tb + 1) // 2                     # 战斗轮次（+1 后取整）
sortie_cost = rounds * 5                   # ★ 出击消耗 = 轮次 × 5
ak = int(summary.get("akashi_encounters"))
ap_bought = compute_monthly_cl1_akashi_ap(instance_name=...)   # ★「当月购买体力」
avg_ap = int(ap_bought / ak + 0.5)         # ★ 四舍五入到整数
net_ap = int(ap_bought) - int(sortie_cost) # ★ 净赚体力 = 当月购买体力 − 出击消耗
eff = net_ap / sortie_cost * 100           # ★ 循环效率
```

REST API `module/statistics/opsi_month.py:48-99`（`get_detailed_summary`）：
```python
battle_rounds = battle_count // 2          # 没有 +1
sortie_cost = battle_rounds * 120          # ★ ×120，不是 ×5
net_stamina_gain = akashi_ap               # ★ 直接是 akashi_ap，不是 net
```

用项目 venv 直接读硬盘库（`get_opsi_stats('alas')`，2026-09）确认：

```
summary()                : total_battles=10120  akashi_encounters=248  siren_research_devices=243
get_detailed_summary()   : battle_rounds=5060   sortie_cost=607200     net_stamina_gain=28540
compute_monthly_cl1_akashi_ap() : 28540
```

对一遍 PC 截图的账：`5060 × 5 = 25300` ✅ 出击消耗；`28540 − 25300 = 3240` ✅ 净赚体力。
**所以 WebUI 页面根本不读 `/api/cl1_stats`**，App 一直在读一个旁路接口。

### 修复方案（**纯客户端，零服务端改动**）
`/api/cl1_stats` 已经包含了全部所需原始值，只是公式不同。**注意一个反直觉的点**：
API 的 `net_stamina_gain` 字段名叫"net"，值其实是 `akashi_ap` ——
也就是 PC 上那个「当月购买体力：28540」。这正好是 App 缺的那个输入。

客户端按 PC 口径重算：

| App 显示 | 计算式（对齐 `app_stat_opsi.py:166-234`） |
|---|---|
| 战斗场次 | `battle_count` |
| 战斗轮次 | `(battle_count + 1) // 2` |
| 出击消耗 | `战斗轮次 × 5` |
| 当月购买体力 | `net_stamina_gain`（= akashi_ap） |
| 净赚体力 | `当月购买体力 − 出击消耗` |
| 循环效率 | `净赚体力 / 出击消耗 × 100`，两位小数 |
| 遇见明石次数 | `akashi_encounters` |
| 遇见明石概率 | `akashi_encounters / 战斗轮次 × 100`，两位小数 |
| 吊机次数 | `siren_research_devices` |
| 吊机概率 | `siren_research_devices / 战斗轮次 × 100`，两位小数 |
| 平均体力 | `int(当月购买体力 / akashi_encounters + 0.5)`（**取整**，PC 显示 115 而非 115.2） |

还要补 PC 有而 App 没有的列：**循环效率、经验效率、平均战斗耗时、平均一轮耗时、今日战斗/今日经验/今日时长**
（后三列需要 `get_ship_exp_stats()`，桥的 `/api/ship_exp` 已有大部分数据）。

### 验收
与 PC「统计 → 大世界数据收集」表格**逐格**对齐（含小数点位数）。

## 3. 「运行中」下方的任务显示英文

### 现象
首页状态卡第一行是「alas 运行中」，第二行的当前任务显示英文键（如 `OpsiScheduling`）。

### 根因
App 的当前任务来自 MCP `get_current_running_task`（`mcp_server_sse.py:330-359`），
它是从日志里正则抠出来的**英文 command**，**原样返回、完全不翻译**：

```python
m = re.search(r"调度器: 开始任务\s*[`'\" ](.*?)[`'\" ]", line)
...
task = m.group(1)          # -> "OpsiScheduling"
```

日志源头的写法也确认了是英文键：
`alas.py:2089` `logger.info(f'[Alas] 调度器: 开始任务 \`{task}\`')`，
其中 `task` = `alas.py:2011` `return task.command`。
实测 `log/2026-09-11_*.txt`：`... | INFO | [Alas] 调度器: 开始任务 \`OpsiScheduling\`` ✅

而 PC 端显示时统一走 i18n：`module/webui/app_dashboard.py:67`
```python
put_text(t(f"Task.{func.command}.name")).style("--arg-title--")
```

**翻译链路**（已逐层确认）：
`t()`（`module/webui/lang.py:37-44`）→ `_t()`（`lang.py:47-57`）→ `dic_lang[lang][s]`，
建表在 `lang.py:63-73`，把 `module/config/i18n/zh-CN.json` 按 `deep_iter(..., depth=3)` 拍平成点号路径。
**确切 key 路径：`i18n["Task"]["<TaskKey>"]["name"]`**（如 `zh-CN.json:285-288` → `"OpsiScheduling": {"name": "智能调度Plus"}`）。

> 顺带一个值得知道的行为：`_t()` 查不到 key 时是 `print(...)` 后**原样返回英文键**（`lang.py:55-57`），
> 所以 PC 端"显示成英文"本身就是"翻译缺失"的信号。

### 修复方案（**纯客户端**）
App 侧**已经有**同源同表的中文索引了，只差接线：
- 数据源：桥 `/api/task_tree`（`bridge/mobile_bridge.py:169-180`）读的正是
  `menu.json` + `i18n/zh-CN.json` 的 `Task.<Key>.name`，与 PC **逐字一致**
- 索引：`data/TaskModels.kt:20-26` `TaskTree.nameOf(key)`
- **已有先例**：`ui/screens/TasksScreen.kt:167`
  `state.taskTree?.nameOf(task.task) ?: taskLabel(task.task)`

**最小改动**：在 `ui/AppViewModel.kt:172`（`currentTask = snap.currentTask`）处就地映射，
这样首页状态卡 / 任务页 / 统计页三处顶栏**一起生效**，比只改 `HomeScreen.kt:59` 覆盖面更大。
显示点本身在 `ui/components/StatusCard.kt:102`。

### ⚠️ 同批次必须一起修掉的隐藏 bug
App 里那张手写的兜底表 `ui/Format.kt:56-79 TASK_LABELS`（22 条）**和 PC 不一致**：

| 任务键 | App 的 TASK_LABELS | PC（i18n 权威值） |
|---|---|---|
| `OpsiScheduling` | 大世界调度 | **智能调度Plus** |
| `Main` | 主线 | **主线图-1Plus** |

任务页因为先走 `nameOf()` 所以显示是对的，但这个兜底表一旦被用到就会显示错误的名字。
**处理方式：不要继续补全它**（93 个任务会随版本漂移），只保留极少数条目作最后兜底，
并在注释里标明"非权威，权威源是 /api/task_tree"。

### 一个语义差异（当前无影响，但要知道）
桥（`mobile_bridge.py:55`）和 MCP helper（`mcp_helper.py:35`）都**硬编码 zh-CN**，
而 PC WebUI 跟随 `deploy.yaml:220` 的 `Language` 设置（`app.py:267`）。
若哪天把 WebUI 语言改成 en-US，PC 会显示 "Smart Scheduling"，App 仍显示「智能调度Plus」。
当前是 zh-CN，一致，不用处理。

### 验收
运行中截图，状态卡第二行显示中文任务名。

## 4. 耄耋相接数据收集没显示

### 现象
App 的「耄耋相接」段落显示空态「暂无耄耋相接数据」，
但 PC「统计 → 耄耋相接数据收集」有两行数据：

| 月份 | 侵蚀等级 | 战斗场次 | 出击轮次 | 平均战斗时间 | 平均一轮耄耋相接时长 | 吊机次数 | 吊机概率 |
|---|---|---|---|---|---|---|---|
| 2026-09 | 3 | 528 | 264 | 17.0秒 | 72.1秒 | 14 | 5.30% |
| 2026-09 | 5 | 96 | 32 | 41.6秒 | 180.7秒 | 3 | 9.38% |

### 根因：App 读错了表
PC 页面 `module/webui/app_stat_opsi.py:309-363`（`_build_meow_rows`）读的是：

```python
for hazard_level in (3, 5):
    meow_data = cl1_db.get_meow_stats(instance, now.year, now.month, hazard_level=hazard_level)
```

即 `module/statistics/cl1_database.py:1084` 的 `get_meow_stats()`，数据落在
**`config/cl1_data.db`** 的 `cl1_data` 表（`cl1_database.py:115-120`）。

而 App 的桥读的是 `log/azurstat_meowofficer_farming.csv`
（`bridge/mobile_bridge.py:56`），那张表的列是

## 5. 日志没有实时同步

### 现象
PC 概览页日志是实时滚动，App 是 30 秒轮询一次 MCP `get_recent_logs`。

### 根因（比预想的更彻底）
**PC 的日志面板根本不读日志文件。** 它读的是父进程内存里的 `ProcessManager.renderables`
—— worker 子进程通过 `multiprocessing.Queue` 推上来的 **Rich 渲染对象**：

| 段 | 位置 |
|---|---|
| worker 子进程把每条日志渲染成 Rich 对象 | `module/logger.py:68-118` `RichRenderableHandler` |
| 跨进程队列 | `module/webui/process_manager.py:147, 731` |
| 父进程内存缓冲（上限 400 条） | `process_manager.py:592-601` |
| 每 0.25s 增量转 HTML 推前端 | `module/webui/widgets.py:236-256`，装配点 `app_overview.py:250` |

→ **端到端延迟 ≈ 250ms**，走的是 PyWebIO 自己的会话 WebSocket（路径就是根 `/`）。

**所以"找到那个日志接口接上去"这条路不存在** —— 全库 grep 确认项目里
**没有任何日志专用的 WebSocket / SSE / HTTP 路由**（`module/webui/api.py:1785-1804`
只有 `/api/cl1_stats`、`/api/ap_timeline`、`/api/notify*`、`/api/launcher/*`、
`/api/deploy/*`、`/obs`，以及 `/ws/live_screenshot`、`/ws/live_control`）。

而 MCP `get_recent_logs`（`mcp_server_sse.py:253-277`）读的是**文件**，而且是全量：

```python
content = f.readlines()        # ← 每次读整个文件
content = content[-lines_count:]
```

实测当前日志 `log/2026-09-11_alas.txt` = **16.2 MB / 12.4 万行**，
所以现在是"每 30 秒整读 16MB，只为拿最后 400 行"。

### 顺带解释了一个现象
文件 sink 和面板 sink 用的是**两套 formatter**（`module/logger.py:371-376`）：

| | 格式 |
|---|---|
| 文件（App / MCP 读的） | `2026-09-11 09:57:35.226 \| INFO \| 潜艇呼叫计时器到达` |
| 面板（PC 看的） | `09:57:35.226 │ 潜艇呼叫计时器到达` + Rich 彩色 level 徽标 |

另外面板把行尾补到浏览器宽度，文件侧固定 **119 列**（`logger.py:132`），
这就是 App 那边要 `trimEnd()` 的原因。
还有：`np.int64(...)` 的清洗**全项目零命中** —— 那是 App 自己加的（`Models.kt:259-260`）。

### 修复方案（推荐）
在 sidecar（沿用现有 `mobile_bridge.py` 模式）新增**按字节 offset 的增量 tail**：

```
GET /api/logs/tail?instance=alas&offset=<bytes>&max_bytes=65536
→ {"success":true,"data":{
     "file":"log/2026-09-11_alas.txt","size":16257570,
     "offset":<新offset>,"reset":false,"lines":[...]}}
```

实现要点：
- `open(path,'rb')` + `f.seek(offset)`，**只在最后一个 `\n` 处截断**，
  未完成的半行留给下次（否则 UTF-8 多字节会被劈开成乱码）
- `size < offset` 或文件身份变化 → 返回 `reset: true`，客户端重取末 N 行
  （天然处理 0 点轮转，`logger.py:233-238`）
- offset 由客户端携带，**服务端无状态** → App 重启/切后台回来不用对账
- 顺手把 `trimEnd()` 和 `np.int64()` 清洗下沉到桥，所有客户端受益

App 侧把轮询改成 **1 秒**，单次只读几十 KB。观感上 ≈ PC 的 250ms，够用了。

### 实现（2026-09-11）—— **已完成**

**桥**：`GET /api/logs/tail?instance=&offset=&tail_lines=&max_bytes=`
- 不传 `offset` → 「首次/重置」模式，给最后 `tail_lines` 行（默认 400，上限 5000）
- 传了 → 从该**字节位置**读增量
- 只在最后一个 `\n` 处截断，半行留给下次；`\r\n` 也处理
- `size < offset` → `reset: true`
- 撞到 `max_bytes` → `truncated: true`，客户端立刻再拉一次
- 清洗（`trimEnd` + `np.int64`）**下沉到桥**，所有客户端受益

**App**：
- `data/Models.kt`：新增 `LogTail`；`mergeLogs` 标注为「**只在桥不可达时兜底**」
- `data/McpClient.kt`：`fetchLogTail()`
- `ui/AppViewModel.kt`：`logOffset` / `logFile` / `logsFromBridge` 三个状态 +
  **独立的 `logJob`**（1 秒一次），只在日志页打开时跑：
  - `openLogs()` 启动、`back()` / `selectTab()` 停止
  - `reset` 或首次 → 整体替换；否则只追加
  - 内存里最多留 3000 行（`LOG_BUFFER_MAX`）
  - `clearLogs()` **不动 `logOffset`** —— 那记的是"文件读到哪了"，和屏幕显示多少行无关
  - `pollOnce` 在 `logsFromBridge` 为真时**不再碰 `logs`**，避免两条路互相打架
- `MainActivity.kt`：`onStop` → `pauseForBackground()`（停日志流 + 停轮询），
  `onStart` → `resumeForeground()`（接回轮询；若还停在日志页，日志流也接回，
  且 **offset 归零重取尾部** —— 后台期间漏掉的不会丢，也不会断层）

> 1 秒一次看着激进，但单次只读几十 KB 增量；和原来「30 秒一次整读 16MB」相比，
> **单位时间的磁盘 IO 反而低得多**。

### 真机验收（2026-09-11 11:47）

日志页在 16 秒里从 **401 行 → 539 行**，新行（`[Alas] 调度器: 开始任务 \`Restart\``、
`应用停止: com.bilibili.azurlane` 等）**实时出现**，自动滚动跟着走。

桥侧同一时刻的增量读数：

```
offset=16594369  size=16594369          ← 追平后 offset == size
6 秒后再拉 → 93 行新增                    ← 增量语义生效
   ─────── 查找并启动委托 ───────
   2026-09-11 11:47:54.481 | INFO | 查找并启动委托
   2026-09-11 11:47:54.485 | INFO | [委托-查找] 正在查找委托 保卫运输部队II | b714de43…
```

### 子代理抓出并修掉的一个真 bug（记一笔）
第一版 `_scan_tail` 在丢掉「开头那截半行」之后，用**缩短后的 blob** 去算续读位置，
导致首次拉取返回的 `offset` 比文件末尾**少 76 字节**；紧接着的那次增量就会吐出
**最后一行的 76 字节残段** —— 正是「重复 + 乱码」那一类。
被用例 1/2 抓到（`offset != size`，且第二次本该空却返回 1 行）。
改成按 blob 在文件里的真实起始位置算 offset，重跑受控 root **25/25 通过**。

### 桥侧的硬证明
- **边写边拉**：并发写 3000 行（含中文），客户端按 `max_bytes=1024` 拉了 302 次
  （期间频繁 `truncated=true`），累计拿到的 3000 行**逐项等于**写入的 3000 行，
  去重后仍是 3000 → 无重复无丢行
- **16.5 MB 真实日志**：首拉 400 行 == 独立整读算出的真实最后 400 行，**3.5 ms**；
  增量 1.6 ms；同期 `readlines()` 整读取尾部 = **78.8 ms**（MCP 那条路每次都要付这个）
- **清洗**：全文件 125,896 行**每一行**都被 Rich 补齐过行尾空格，
  4,791 行含 `np.*(...)` 泄漏（9,830 处）；接口返回里行尾空白条数 = 0
- **半行 / 轮转 / 非法实例 / 文件不存在**：各有专门用例

### 客户端补的一处防护
子代理提醒：桥是无状态的，唯一能自己发现的轮转判据是 `size < offset`；
日志页**跨过 0 点没退出**时，新文件长到比旧 offset 还大，第一拉会从今天文件中间开始。
→ App 侧加了「`tail.file != state.logFile` 也算 reset」（`pullLogTail`）。

### 这个方案还顺手修掉一个 bug
App 现在的日志合并 `Models.kt:269-278 mergeLogs` 用的是**锚点去重**
（拿上一轮最后一行从后往前找）。而日志里 `潜艇呼叫计时器到达`、
`[战斗UI] PAUSE_OldeRoyal` 这类重复行极常见 → **会误判，导致重复显示或丢行**。
改成字节 offset 之后，这一类问题整类消失。

### 明确不走的两条路
- ❌ **直接把 `get_recent_logs` 的轮询频率调高**：每次全量读 16MB，
  而且一次 snapshot 要建 MCP 会话 + 5 次 tool 调用（`McpClient.kt:346-387`），
  还会在父进程事件循环里做阻塞 `readlines()`。调到 1 秒会明显伤盘。
- ❌ **直连 PyWebIO 的 WebSocket**：那是会话级 UI 协议通道，
  推的是 `run_script` 命令 + 带内联样式的 HTML，不是文本行；
  且不是公开 API，跨版本易碎。

### 升级安全性（已确证）
`deploy/git.py:129,132` = `git reset --hard` + `git pull --ff-only`，**没有 `git clean`**。
→ 往 `module/webui/*`、`mcp_server_sse.py` 这些**被跟踪**文件里加日志路由，升级后 100% 丢失；
做成**未跟踪的 sidecar** 才活得下来。这条约束决定了方案只能是 sidecar。

### 遗留风险
- 未跟踪文件躲得过 `reset --hard`，但躲不过手敲 `git clean -fd`
- sidecar **没有自启机制**，重启 PC 后不会自己起来（全库 grep 确认无任何引用）
  → App 侧应该做健康检查（已有 `/api/health`）并明确提示「数据桥未启动」，
  现有文案在 `SettingsScreen.kt:211` / `StatsScreen.kt:207`

## 9. 一句话总结

五个问题分两类：

**第一类 · 数据源错了**（侵蚀1、耄耋相接）—— App 读了一个 PC 页面根本不用的旁路接口。
修法是让 App 走 PC 页面同源的函数/数据。

**第二类 · 数据源对、规则不对**（队列）—— 实测证明 WebUI 和 MCP 是**同一个进程、同一份配置**，
19 个启用任务逐字相同；差别只在拿到之后：少一个桶、排序键从"优先级序"变成"时间序"、没翻译。
这类问题**不会有报错，只会静静地显示成另一个样子**，所以最难发现。

加上两个纯缺失功能（任务名翻译、日志实时性），一共五条。

**统一方针：不在客户端"把数字调对"，而是让 App 复用 PC 端的同源逻辑。**

## 16. 问题 1 · 队列三段（2026-09-11）

### 判据
PC 概览页是三段（界面骨架 `app_overview.py:64-87`，填充 `app_dashboard.py:35-58`）：

```python
if len(pending_task) >= 1:
    if self.alas.alive:
        running = pending_task[:1]      # 第一个就是正在跑的
        pending = pending_task[1:]
    else:
        running = []                    # ★ 停止时运行中清空
        pending = pending_task[:]       # ★ 全部留在队列中，一个不减
else:
    running = []; pending = []
```

**最容易漏的是 `else` 那一支**：停止状态下三段的分母不一样。App 之前只按时间切两半，
所以「谁在跑」无从谈起，硬切会把本该在「运行中」的那个也留在队列里。

### 分工
「运行中」这一段取决于 `alive`，而 **`alive` 只有 App 知道**（MCP `get_status`），
桥是独立进程拿不到。所以：
- **桥**：只做「分组 + 排序」，返回 `pending` / `waiting`
- **App**：用 `splitOverview(alive, pending, waiting)` 切出「运行中」，逐行对齐上面那段 Python

这个切分放在 `data/Models.kt` 的 `splitOverview()`，KDoc 里贴了 PC 的原文。

### App 侧改动
- `data/Models.kt`：`ScheduledTask` 加 `name`（桥给的中文名）；
  新增 `OverviewBuckets` / `splitOverview()`
- `data/McpClient.kt`：新增 `fetchOverviewTasks()` → 桥的 `/api/overview_tasks`
- `ui/AppViewModel.kt`：新增 `overviewPending` / `overviewWaiting` / `overviewLoaded`；
  `pollOnce()` 末尾调 `loadOverviewQueue()`（放在 MCP 快照之后 —— 切「运行中」要用到刚拿到的 `running`）；
  **桥不可达时不清空旧数据**，只把 `overviewLoaded` 置 false，让界面退回 MCP 的近似切法
- `ui/screens/TasksScreen.kt`：改成三段（运行中 / 队列中 / 等待中），
  每段各有符合语义的空态文案；桥在线用桥的顺序，离线退回 `splitQueue()`

### 真机验收（2026-09-11 11:25）

**停止状态：**

| 分段 | 内容 |
|---|---|
| 运行中 (0) | 「当前没有任务在运行 / 实例已停止。启动后第一个到点的任务会出现在这里。」 |
| 队列中 (2) | **委托 10:50** → **智能调度Plus 09-09 00:00** |
| 等待中 (17) | 演习 12:00 → 大舰队 12:00 → 收获 12:00 → … |

**启动后（同一份队列，只变了 alive）：**

| 分段 | 内容 |
|---|---|
| 运行中 (1) | **委托** ← 从「队列中」提到这里 |
| 队列中 (1) | 智能调度Plus |
| 等待中 (17) | 不变 |

两处关键证据：
1. **顺序是优先级序，不是时间序** —— 智能调度Plus 的 NextRun 是 `09-09`（更早），
   但排在「委托」（`10:50`）**后面**。默认优先级表里 `Commission` 位次 2、`OpsiScheduling` 位次 67。
   接桥**之前**这里是反的（时间序），接上就对了。
2. **`alive` 分支生效** —— 停止时「运行中」清空、全部留在「队列中」；
   启动后第一个 pending 提到「运行中」。

### 桥侧的保真度证明
子代理用**冻结快照 + 冻结时钟**（把 `OpsiAshBeacon.NextRun` 改回 `09-11 09:57:48`、
时钟冻结到 `10:19:00`），把桥的输出和项目自己的
`Filter(regex="(.*)", attr=["command"])` + `parse_value` + `attrgetter("next_run")` 流水线对比：

- `PRIORITY IDENTICAL: True` —— 优先级串 75 项**逐字节相同**
- `PENDING IDENTICAL / WAITING IDENTICAL: True` —— 含 nextRun 字符串，并列项顺序也一致
- `MATCHES USER SAMPLE: True`

### 已知偏差（子代理主动报告，都写进代码注释了）
1. **`TaskHoardingDuration` 没实现**。PC 有 `now -= hoarding`（`config.py:318-319`），
   当前 `Alas.Optimization.TaskHoardingDuration = 0` 是空操作，所以桥按 `next_run < now` 实现。
   **如果以后把这个值调大，边界 N 分钟内的任务可能分错桶**。
   另外 PC 还有运行时的 `is_hoarding_task` 开关，桥作为独立进程拿不到。
2. **时间源**：PC 用 NTP 校时后的时间（`time_source.now()`），桥用本机 `datetime.now()`。
   两机时钟偏差大时，恰好卡在边界上的任务可能分桶不同。日常无影响。
3. 桥的返回体比 App 需要的多给了 `instance` / `now` / `unmatched` 三个字段。
   App 用的是 `org.json` 的 `opt*`，**自动忽略未知键**，没有风险。
4. `NextRun` 缺失/空串按 PC 的 `config_update` 语义补成 `2020-01-01 00:00:00`
   → 走优先级排序进 pending（**不是** error 分支）。
   `NextRun` 解析失败的 error 分支也实现了（会拼在 pending 最前面），当前数据不可达。

## 19. 资源行对齐修正（2026-09-11）
用户反馈两点，都改了：

**① 从钻石开始，后面的数字偏上。**
根因：上一版把数字放在**第一行内部**居中，而数字（`NumeralValue` / `NumeralHero`）
字号比标签大、行高也不同 —— 一旦只在第一行里居中，基线就会随字号飘。
观感就是"前两行看着还行，从某一行开始数字翘上去了"。

改法：把数字提到**外层 Row**，相对**整个两行块**垂直居中。
这样不管数字是 30sp 还是 22sp，都稳稳落在整行的视觉中心。

**② 行动力的「(2,993)」挤在第一行**，和「上限」不是一套。

用和「上限」完全相同的浅灰（`textTertiary`）—— 它们是同一层级的信息：
一个静态的、参考用的数字，不该和主数值抢注意力。

现在第二行右侧那一格按优先级取：
```
有上限   → 上限 11,200      （超上限时「上限」两字染警示色）
只有总量 → 总行动力 2,993
都没有   → 空着
```

**① 状态栏图标不跟随应用内主题**（P0-5）
窗口属性原本由静态 XML 决定，而主题是 `AppRoot` 用 `state.themeMode` 覆写的。
于是**系统浅色 + 应用内选深色 ⇒ 深底配黑图标，看不见**；反过来也一样。
加剧因素：manifest 的 `configChanges` 含 `uiMode`，系统切换深浅色时 Activity 不重建，
XML 属性根本不会重新解析。

改法：在 `AppRoot` 里用 `SideEffect` + `WindowCompat.getInsetsController(...)`，
按 `dark` 实时设置 `isAppearanceLightStatusBars` / `…NavigationBars`。
放 `SideEffect` 里顺带把 `uiMode` 不重建的问题一并解决了。

**② 大标题的字距符号是反的**（P1-3）
`headlineMedium` 原来是 28sp Bold + `letterSpacing = -0.7sp`，
而 HIG 的字距表里 34pt 是 **+0.37pt（正值）**。负字距会把大标题挤扁 ——
这是全工程最明显的一处排版错误。已改成 **34sp Bold / +0.37 / 行高 41**（HIG Large Title 档）。

> ⚠️ 用的是 Inter 不是 SF Pro，Inter 原始字距更紧。数值当量级参考，真机截图对齐过。

按用户点名的四项改，全部真机验证。

### 1 · 资源行统一高度、去掉进度条
`components/ResourceCard.kt` 的 `ResourceRow` 重写成**结构完全统一**的两行：

```
● 石油                        4,271

```

- **不放进度条**。石油/物资的上限是 OCR 出来的、会变，条子只是在

### 2 · 时间与上限位置互换
原来是「上限在左、时间在右」，现在**时间在左、上限在右**。
理由：时间是"这条数据可不可信"的判据，扫视一列时它应该对齐在同一条竖线上；
上限是静态属性，放右边不抢注意力。

### 3 · 启停按钮的旋转弧线
参考图里是「方块图标 + 旁边一道绿弧」。照做了结构，但**配色用主蓝而不是绿** ——
绿在这个 App 里是「成功」的语义（轻提示的语气点就是绿的），拿来表示"正在跑"会打架。

运行中时：外圈一道 78° 的圆头弧线绕按钮转（1.5 秒一圈）+ 一层静止的柔光底。

### ⚠️ 顺带修掉一个潜伏很久的真 bug
`Size.kt` 的 FAB 外层容器是 `.size(FAB_SIZE)`（62dp），它会把子项约束**收窄回 62dp**。
而弧线画布和原来那个「呼吸光晕」都是 `FAB_SIZE + 18dp` —— **一直被压成 62dp、
正好落在按钮边缘被盖住，所以那个光晕从来就没有显示过**。

改用 `Modifier.requiredSize()`（忽略父约束），再靠 `Box` 默认不裁剪把弧线画到按钮外面。
**这个 bug 靠读代码发现不了**——它只在真机截图放大之后才看得出来。

## 14. 只读参数：任务优先级调整（2026-09-11）

**要求**：通用设置里的「任务优先级调整」在 App 中**只显示「请在 PC 端调整」，点击无反应**。

**判据用类型，不用路径。** 这个参数是
`General.YukikazeTaskManager.TaskPriorityAdjustment`，`args.json` 里 `type = "task_priority"`，
而且**全项目只出现这 1 次**（已核对）。所以规则写成「`type == "task_priority"` 即 PC-only」，
比写死一个路径稳。

**为什么不让它在手机上改**（也写进了代码注释）：
- WebUI 里它是个**拖拽排序列表**，手机上没有对应交互；
- 它的值是一大段多行文本（默认就 20+ 行），手机上编辑几乎必然出错；
- 一旦存坏，**调度顺序会整个乱掉，而用户很难发现**。

**实现**（三处小改）：
- `data/TaskModels.kt`：`ConfigArg.isPcOnly = (type == "task_priority")`
- `ui/screens/TaskConfigScreen.kt`：`when` 里加 `item.isPcOnly -> PcOnlyRow(...)` 分支，
  放在 `else`（可点行）之前
- 新增 `PcOnlyRow`：**完全没有 `clickable`**（不是"点了没反应"，是压根没有点击语义，
  连按压高光都没有）、**没有右箭头**（箭头是"点进去还有一层"的承诺，这里没有下一层）、
  右侧写「请在 PC 端调整」而不是把那个多行值显示出来

**真机验证**（`通用设置 → 雪风大人的任务管理 → 任务优先级调整`）：
- 显示 `任务优先级调整` + 帮助文案 + 右侧灰色 `请在 PC 端调整` ✅
- 点击前后截图逐像素一致（唯一差异是状态栏时钟 11:07→11:08），无弹窗、无高光、无导航 ✅
